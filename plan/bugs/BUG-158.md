# BUG-158: 操作中・放置中にフリーズし、電源ボタンの長押しが要る

Reproduction: reproduced（S1（2026-10-03、Latitude 5330、素の USB 起動、ユーザー、[結果](../ws133/s1-results.md)）、2 回）
Disposition: tracking（WS005／WS004（AX211）、原因次第）
Discovery: 安定版 S1 の実機試験（[WS133](../ws133/ws.md)）

M650（Logi Bolt）を挿して再 login 後 1 分ほどの放置、と M650 を抜いてタッチパッドで窓を移動中。その後は出ていない。user「フリーズはおそらく、WiFiが未接続のときに起きています。」→ WiFi 未接続の間の networkd の自動の探索（AX211 の scan・join の繰り返し）と kernel の WiFi・driver の経路が第一の候補。読みで候補を絞り、実機（S2）で SSH をつないだまま再現して kernel 全体の停止か compositor だけかを分ける。

## 読みでの原因の候補（2026-10-03、q638、P1。実装していない）

読みで 1 つに絞れる証拠は無い。候補と S2 で分ける方法:

1. **AX211 の自動の探索の経路で kernel の thread が長く回り続ける。** WiFi 未接続の間、networkd は保存済みの network を探して scan・join を
   繰り返す。AX211 の driver には `sched_yield()` で待つ loop（`ax211_pci_operations_join_locked`、`ax211_pci_station_close_wait`、
   `intel-ax211-pci-mmio.c` の時間待ち）と、TX の timeout からの recovery（`ax211_pci_recovery_latch_locked` → `recovery_run_locked`、
   session stop・quarantine）がある。network の worker と利用者の thread は同じ優先度（`SCHED_PRIORITY_DEFAULT` 8）なので完全な飢餓には
   ならない見込みだが、recovery の繰り返し・interrupt の嵐・spinlock を持ったままの長い待ちがあれば画面ごと止まる。
2. **GPU（i915）の停止。** 画面と cursor が止まり入力も効かないように見える症状は、kernel が生きていても compositor の present が戻らなければ同じ。
   S1 ではバッテリーで GPU が遅くなった観察もある。WiFi との相関は偶然の可能性。
3. **入力の経路（xHCI・HID の M650 と PS/2 の touchpad）。** 1 回目は M650 を挿して放置、2 回目は M650 を抜いて touchpad で窓を移動中。両方とも
   pointer の入力に関わる。`ps2-8042.c` は controller_lock（spinlock、irqsave）を持ったまま input の emit をする所がある。

S2 で分ける方法: SSH をつないだまま（有線の USB LAN で）再現させ、(a) SSH が答えるか（kernel 全体か compositor だけか）、(b) 答えるなら
`ps`・zdesktop の log・kernel log（`intel-ax211: recovery`、`i915` の hang、input）を読む、(c) 答えなければ WiFi を off にして同じ放置で再現するか
（WiFi の経路の切り分け）。gdbstub が使えない実機なので、kernel log を serial や SSH で外へ逃がすのが要る。
