# BUG-142: Files の起動直後の present の停止中の Ctrl+C が次の click の後に処理される

Reproduction: unreproduced（q616-i01 で調べ、QEMU で再試行せず。source の上では順序は保たれる）
Disposition: scheduled（ws099-p028、2026-10-03。元は tracking、実機の ws127-p007）
Discovery: ws127-p001 / q595、[requirements](../ws127/requirements.md) §3 の B2。Ctrl+C が次の click の後に処理され、Ctrl+V が「Nothing to paste」。

## q616-i01（P1、2026-10-03、ws127-p002）: 調べ（限定、修正なし）

- zdesktop（`wayland/menu-shell.c` の `zwl_menu_key`）は shortcut の key の press の時に、その場で `activated` を送る（pointer の event と同じ
  接続・同じ順）。Files（`files/menu.c` の `menu_activated`）は action を `fm_window_action` で pointer・key と同じ queue に積み、順に処理する。
  source の上では Ctrl+C と次の click の順は入れ替わらない。
- P4 の 1 回の観察は、起動直後の 2.6 秒の present の停止の間に QMP で入れた入力の時に起きた。入力の注入の順（QMP の pointer と key は別の
  経路）か、zdesktop の側での key と pointer の処理の順の可能性があり、Files の直しの対象は見つかっていない。
- 次: 実機（5330）の通し（ws127-p007）で、起動直後に選択 → Ctrl+C → すぐに sidebar の click を試す。再現したら zdesktop の入力の順（P2 の
  compositor の担当）と合わせて調べる。

## 2026-10-03 ws099-p028（q645、P2、コードの読みと直し）

候補を compositor に見つけて直した: event loop（`main.c`）は ready な入力 device を 1 つずつ順に全部読んでいたので、zdesktop が忙しい間に
keyboard（Ctrl+C）と tablet（click）の両方に event がたまると、device の slot の順で適用され、click が先に Files に届きうる。`input.c` の
`zwl_input_read_devices` で ready な device を evdev の時刻の順に merge して適用するようにした。試験 `plan/ws099/tests/bug142-order.sh`
（zdesktop を SIGSTOP して Ctrl+C → click → SIGCONT、Files の log の順と Ctrl+V の結果）。QEMU は T1 に依頼（結果待ち）。Disposition は scheduled（ws099-p028）。
