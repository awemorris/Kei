# BUG-145: AX211 で 4-way handshake の後に DHCP の lease が取れず、AP から disassociation（reason 8）

Reproduction: reproduced（P1 / q611、5330 の AX211 passthrough、5GHz の試験用 AP、7 回とも）
Disposition: tracking（WS004 の新しい Phase の候補）
Discovery: ws005-p019 / q611（2026-10-03）。WPA2-PSK の 4-way handshake は成功（authorized=1、鍵は正しい）が、DHCP が時間切れ・ECONNRESET・ENODEV・ENETDOWN。gdbstub で捕まえた ECONNRESET は AP からの Disassociation reason 8。AX211 driver の association の後の data path の問題と推定（未解析）。実機の単独起動での接続の可否はユーザーの以前の試験と照らす。
Note: 2.4GHz の試験用 AP は WPA3-SAE 専用（PMF required、PSK 無し）で、networkd（WPA2-PSK）の対象外のため試せなかった。

2026-10-03 user:「elecom-84a0c3は、過去に接続できた実績があります。WPA3だけでなく、WPA2-PSKも受け付けるような気がします。本当にWPA2を受け付けないか、確認してください。…5GHzのAPも、過去にはきちんと接続できていた実績があります。2.4GHzでは少なくとも、IPアドレスが取れて、外部通信まで成功した実績があります。それはパススルーでも実機でも同じです。」→ **回帰**として扱う。2.4GHz の AP の「WPA3 専用」の判定（RSN の AKM の解析）が正しいかを確かめ、最後に動いた版（ws004-p038/p041 の頃）からの変化を二分して原因を探す。

2026-10-03 / 5330 の host の停止: q612 の passthrough（iGPU・AX211・usb-net）の起動の直後に host が止まり、ユーザーが再起動。host の journal は 00:41:49（vfio-pci の reset の 4 秒後）で途切れ、panic の記録・pstore は無い（hard hang の見当）。前の 2 回の同じ harness は正常。

2026-10-03 user:「BUG-145は、WPA3しか使えないという結論になったら、それは何かがおかしいので、BUG-145を後回しにして、デスクトップの機能性を追加するWSの実行にサブエージェントを再利用してください。」

2026-10-03 01:27 / 5330 の host の 2 回目の停止: AX211 だけの passthrough（iGPU 無し、std VGA）でも、QEMU の起動の約 2 分後に host に届かなくなった（ARP INCOMPLETE）。2 回の停止の共通点は image `build/p1-wdesk24`（p024 の networkd/sessiond と試験用 service）。q611 の 2 回（`build/p1-wdesk`）は正常に戻った。前回の journal は vfio の reset の 4 秒後で途切れており、guest の software より QEMU 起動時の AX211 の vfio の扱い・host 側の疑いも残る（未解析）。ユーザーが不在のため再起動を待つ。5330 の passthrough は、原因が分かるまで使わない（朝にユーザーに確認）。

2026-10-03 08:30 / 2 回目の停止の host の journal（ユーザーの再起動の後に Q1 が確認）: 01:27:53 の QEMU の起動で、AX211（00:14.3）の vfio-pci の reset が **3.4 秒**かかり（01:27:54.49 → 57.86、1 回目の停止の前の boot では約 0.1 秒）、続く 2 回目の reset は即時に終わった。journal は 01:27:58（systemd-rfkill の終わり）で途切れ、panic・pstore の記録は無い。AX211 の FLR/CNVi の reset の異常から host が固まった見当（未証明）。ユーザーの指示で、WiFi の試験は 5330 の AX211 ではなく host（開発機）に挿した Realtek の USB の WiFi（TP-Link 2357:0138、RTL8822BU）を local の QEMU に USB passthrough して行う。

2026-10-03 q626（RTL8822BU の USB passthrough、local の QEMU）: scan で両 AP が見え、2.4GHz の AP の security の印は `0x1b5`（WPA2+CCMP+PSK+SAE+PMF-capable、以前の q069 の evidence と同じ）で WPA3 専用の誤判定は無い（AX211 の q611 の `0x395` は AX211 側の RSN の扱いの疑い）。2.4GHz の connect は association と 4-way handshake が通る（authorized=1）が、直後に DHCP が EIO。wlan0 の TX は 0、RX は errors だけ増える。AX211 と同じ「handshake の後に data が通らない」症状なので、driver ではなく共通の wlan の data path（station の送信・L2 の組み立て・受信の復号）か DHCP の回帰の疑いが強い。

2026-10-03 q627（P1、RTL8822BU の USB passthrough、local の QEMU、commit `0c9cf7178`・`865c8d536`・`d2c2bc1d2`）: 「handshake の後に data が通らない」の
RTL での原因は driver ではなく共通の IPv4 の出力: 有線（ue0）の default route がある時、dhcpc の broadcast（SO_BINDTODEVICE wlan0）の next hop が
ue0 の gateway になり ARP で止まっていた（gdbstub の trace）。`ipv4_output_common` を指定 device の route だけに限り、limited broadcast は gateway に
送らないよう直した → 2.4GHz・5GHz とも lease・ping・外部の fetch（WiFi 経由）が通る。併せて直した: 5GHz の scan の channel（HT Operation の primary）、
networkd の有線の policy が wlan0 を有線として down していた件、有線の removal で WiFi に default が戻らない件（ws005-p020 の q627 の結果）。
AX211 への影響（見込み）: q611 の AP2 の「DHCP の時間切れ」2 回は有線を付けたままの run で、修正 1 と同じ経路の可能性が高い。「device_del の後の
ECONNRESET（AP の disassociation reason 8）」は修正 1 では説明できない。また AP1 の SSID は各 band に WPA2/SAE 混在（0x1b5）と WPA3 専用（0x395）の
2 つの BSS を持つので、q611 の 0x395 は WPA3 専用の BSS を見ていた可能性が高い（AX211 で 0x1b5 の BSS が見えないなら AX211 の scan の問題）。
AX211 の実機の確認はユーザー（5330 の passthrough は使わない）。Disposition は tracking のまま（AX211 の未確認のため）。
