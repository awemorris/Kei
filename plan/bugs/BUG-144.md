# BUG-144: App Home から 8 番目に開いた Model viewer が vkAllocateMemory -4 で失敗する

Reproduction: reproduced（P4 / q606、QEMU Venus のみ。単独では動く）
Disposition: tracking
Discovery: ws129-p010 / q606。7 つの app を開いた後の mview が `vkAllocateMemory result=-4`（OUT_OF_DEVICE_MEMORY）。QEMU の Venus の host GPU の memory（hostmem=256M）が尽きた見当。実機では未確認。app の数が増えた時の device memory の失敗の扱い（app が error を出して終わる、compositor は影響なし）を確かめる。

2026-10-03 user（優先度と依存）: 標準。WS131 の libkeiland の再構成の後。

## 測定の準備と見積もり（2026-10-03、q643、P1）

handling: [ws014-p011](../ws014/phase011/phase.md)。user の依頼（CPU・GPU の memory の量、BUG-120 と同じか）に答えるため、先に測る。
読みの見積もり: mview 1 個は texture 約 40 MiB（mipmap 込み、device-local）、頂点・index 約 1.2 MiB、host-visible の staging 4〜5.3 MiB（一生 map）。
Venus の上限は host-visible の aperture（hostmem 256 MiB、first-fit）で、device-local は使わない → mview だけでは尽きず、全 app の合計の見込み。
BUG-120 は i915 の object の枠 128 で別の仕組み（同じ形の固定の枠）。実機では mview 5〜6 個で BUG-120 に先に当たる見込み。
kernel に aperture の内訳の診断の log を足し、`plan/ws014/tests/aperture-bug144.sh` を T1 に依頼。数字が出たら user の助言を待って直す。

## 訂正と意味の修正（2026-10-03、P1）

-4 は `VK_ERROR_DEVICE_LOST`（上の「OUT_OF_DEVICE_MEMORY」は誤り）。Venus の aperture の満杯（kernel の ENOSPC）を libvulkan が DEVICE_LOST に変えて
context を失わせていた。ENOSPC を OUT_OF_DEVICE_MEMORY にする修正を入れた（BUG-124 と同じ原因）。容量の修正は測定と user の助言の後。

2026-10-03 T2-001（QEMU、zdesktop の image、ac703b04b、staging の解放 5dc589d7a を含む）: hostmem=1G で mview 14 個とも起動・aperture full 0。hostmem=256M では mview 3 個まで、4 個目で `vkAllocateMemory result=-2 errno=8`、`venus: aperture full context=19 request=5595136 aperture=268435456 used=265228288 blobs=103 largest_hole=2572288`。context 16〜18（mview）は各 53,100,544 bytes・21 blobs、context 0 は 41,779,200 bytes・15 blobs。→ mview 1 個が窓を約 50.6 MiB 使う（読みの見積もりの staging 4〜5 MiB より大きい。texture などの device-local の確保も窓を使っている見込み）。
